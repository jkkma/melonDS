# melonDS Vulkan Renderer — Research & Implementation Plan

*Status: proposal, revision 2. Grounded in the tree at `d3cd616` (post-blackmagic3, compute renderer with tile-size scaling).*

**Revision 2** rewrites revision 1 in response to `docs/vulkan-renderer-plan-review.md`, which put the original through nine independent review lenses plus adversarial refutation. 24 findings survived; all are addressed here. The corrections were concentrated in one place: **revision 1 repeatedly treated behaviour the OpenGL driver provides for free as a property of the code being ported.** GL's implicit in-order buffer guarantee, its driver-side shader compilation, and its per-draw state mutation all have no Vulkan equivalent, and revision 1's memory table, sync model, shader-toolchain claim and 2D-port estimate each rested on one of them. A changelog is at the end.

Two framing statements that revision 1 did not make and that everything below depends on:

- **There is no external existence proof that this port succeeds.** Revision 1 cited two; neither survived checking (§1.3). Every estimate here is unanchored engineering judgement and is labelled as such.
- **Upstream's appetite for a Vulkan backend is unmeasured** — not hostile, not favourable, unknown. Revision 1 asserted a policy that does not exist. Plan this as a fork deliverable until someone asks upstream directly (§4).

## Part 1 — Research summary

### 1.1 How melonDS renders today

The core owns one top-level `Renderer` (2D + 3D + compositing, `src/GPU.h:833-876`) which owns two `Renderer2D` units and one `Renderer3D` (`src/GPU.h:873-875`). Three stacks exist:

| Stack | Parent | 3D | Output |
|---|---|---|---|
| Software | `SoftRenderer` (`GPU_Soft.*`) | `SoftRenderer3D` | RAM, 256×192 **BGRA8888** (`ExpandColor`, `GPU_Soft.cpp:428-445`); the 3D layer is pulled per scanline via `GetLine` in packed 6:6:6:5 |
| Classic GL | `GLRenderer` (`GPU_OpenGL.*`) | `GLRenderer3D` (`GPU3D_OpenGL.*`) | GL texture, polygon-based, GL 3.2+ |
| GL compute | `GLRenderer` | `ComputeRenderer3D` (`GPU3D_Compute.*`) | GL texture, tile-based compute rasterizer, GL 4.3 |

Facts a new backend must respect (all verified in-tree):

- **Rendering is *dispatched* from the emu thread; the software rasterizer runs on its own worker thread by default.** `GPU3D_Soft.cpp:48-58` creates it, `:1774-1805` is where rasterization actually happens, and `Config.cpp:99` defaults `{"3D.Soft.Threaded", true}`. `RenderFrame()` is fire-and-forget — `GPU3D_Soft.cpp:1756-1760` posts a semaphore and returns — and **`GetLine` is the sync point — a *per-scanline* one**: it waits `Sema_ScanlineCount` once per line (`GPU3D_Soft.cpp:1816-1822`), so producer and consumer overlap incrementally down the frame rather than at a single barrier. A Vulkan backend must reproduce that asynchrony; it is what makes Phase 2 tractable, and it is why a single wait at line 0 is a different animal from what the tree does today. (Revision 1 said "all rendering happens on the emu thread", which contradicted its own later bullets.)
- **Frame timing.** `RenderFrame()` is invoked at VCount==215 HBlank (`GPU.cpp:1163-1166`), `FinishRendering()` at the *next* frame's VCount==192 (`GPU.cpp:1289`). But the consumer deadline is much shorter: a software-composited pairing starts pulling output via `GetLine` at the next frame's VCount==0, ~48 scanlines after submission. **In emulated time that is ~3 ms at 100% speed — but there is no intra-frame pacing anywhere** (`NDS.cpp:924-1010`; all pacing is post-frame in the frontend, `EmuThread.cpp:311, :323, :361-405`, with `curFPS=1000.0` when unlimited). At 300–600% the real deadline is ~0.5–1.0 ms, and under fast-forward it approaches zero. **The readback deadline is hardest on *fast* hosts, not slow ones.**
- **Two output contracts** (`Renderer::GetFramebuffers`, `GPU.h:860-862`): return `true` + RAM 256×192 pointers (software), or `false` + a backend handle. The `false` path is a raw `*(GLuint*)` cast in the frontend (`Screen.cpp:1150`) — a type-unsafe seam that must be generalized.
- **The software compositor pulls the 3D output line-by-line** via `Renderer3D::GetLine(line)` with `RenderXPos` scroll applied (`GPU_Soft.cpp:115`, contract `GPU3D.h:336-338`); GL renderers return `nullptr` and composite GPU-side. **`GetLine` has a hard non-null contract**: `GPU_Soft.cpp:115` assigns unconditionally for every line < 192 and consumers dereference with no guard (`GPU2D_Soft.cpp:373-375`, `GPU_Soft.cpp:282`). `SoftRenderer3D` always returns a valid pointer, including on its black-line abort branch (`GPU3D_Soft.cpp:1807-1814`).
- **`RestartFrame` means re-render, not discard.** `SoftRenderer3D::RestartFrame` (`GPU3D_Soft.cpp:1768-1772`) calls `SetupRenderThread`, which waits, resets and *re-issues* the frame (`:48-88`). Call site: `if (GPU3D.AbortFrame) { Rend->Restart3DRendering(); GPU3D.AbortFrame = false; }` (`GPU.cpp:1191-1194`). Separately, **while `AbortFrame` is set** (`GPU.cpp:1389`), `GetLine` returns a black line *without waiting* (`GPU3D_Soft.cpp:1807-1814`) and `FinishRendering` skips its wait (`:1740-1743`). `AbortFrame` is savestated (`GPU3D.cpp:535`), so it can be true before the first submission after a state load.
- **Renderer selection/hot-swap**: `EmuThread::updateRenderer()` (`EmuThread.cpp:858-889`) switches on config `3D.Renderer` and calls `NDS::SetRenderer`; `GPU::SetRenderer` (`GPU.cpp:315-344`) syncs VRAM captures and Init/Resets the new renderer. **The "free software fallback" is narrower than revision 1 claimed and does not cover the pairing this plan builds:** `GPU.cpp:323/337` call `Init()` only on the *top-level* `Renderer`, and `SoftRenderer::Init()` is `bool Init() override { return true; }` (`GPU_Soft.h:34`) — it constructs its children at `GPU_Soft.cpp:36-38` and never Inits them. `GLRenderer` is the only renderer that propagates (`GPU_OpenGL.cpp:237-239`). The fallback is also **silent** (`GPU::SetRenderer` is `noexcept` with `// TODO: report error to platform` at `:328-331`; no renderer-kind accessor exists) and **hardcoded to full `SoftRenderer`** (`GPU.cpp:334-338`). Making it usable is Phase-2 work, not free plumbing.
- **`GPU::SetRenderer` destroys before it constructs**: `Rend = std::move(renderer)` at `:322`, with no wait-idle anywhere.
- **Renderer state is not savestated.** `PreSavestate`/`PostSavestate` bracket serialization (`GPU.cpp:209,311`); the software renderer drains its render thread there.
- **VRAM display capture requires GPU→CPU readback**: `AllocCapture`/`SyncVRAMCapture` (`GPU.h:857-858`) — GL uses `glReadPixels` of a downscaled capture buffer (`GPU_OpenGL.cpp:843-912`). This is the only mandatory readback.
- **Frontend/windowing**: Qt is *not* coupled through `QOpenGLWidget`. `ScreenPanelGL` is a native, Qt-never-paints widget (`WA_NativeWindow`, `WA_PaintOnScreen`, null `paintEngine()`, `Screen.cpp:868-878, 1350-1353`); contexts come from the vendored DuckStation layer (`src/frontend/duckstation/gl/`) created against native handles collected into `WindowInfo` (`window_info.h` — Win32/X11/Wayland/macOS). **`WindowInfo` already carries every native handle Vulkan WSI needs.** Up to `kMaxWindows`=4 windows per instance (`EmuInstance.h:32`), up to `kMaxEmuInstances`=16 instances (`main.cpp:75`), each with its own emu thread.
- **A borrow/park protocol already exists** and is the only thing making UI-thread surface work legal: `borrowGL`/`returnGL` (`EmuThread.cpp:686-697`), which DoneCurrents every window's context (`EmuInstance.cpp:417-424`) and parks the emu thread on a condition variable (`EmuThread.cpp:661-666`). It is invoked from exactly two places, both in `Window.cpp` (`:827-828`, `:843-844`), and only when `windowID != 0`. **Two defects to inherit knowingly:** the panel delete at `Window.cpp:813-815` happens *outside* the park, and the park has a lost-wakeup race (the semaphore is released at `EmuThread.cpp:657` before the emu thread reaches the wait at `:664`).
- **Build system**: GL is gated by `ENABLE_OGLRENDERER` → `OGLRENDERER_ENABLED` (`src/CMakeLists.txt:97-109`, `qt_sdl/CMakeLists.txt:276-282`), tested in exactly four source locations. Shaders are embedded as strings at build time via `cmake/MakeEmbed.cmake` (`src/OpenGL_shaders/CMakeLists.txt:30-47`) and compiled by the driver at runtime. **`ENABLE_OGLRENDERER=OFF` does not build today** — six compile errors and three link errors (§Phase 1); no CI job has ever exercised it. There is **zero Vulkan code anywhere in the tree**.
- **Config hazard**: the `renderer3D_*` enum values are positional ints persisted to TOML *and* wrapped in `#ifdef OGLRENDERER_ENABLED` (`EmuInstance.h:71-79`). The hazard is already live: with the flag OFF, `renderer3D_Max` is 1 and `Config.cpp:80` clamps `3D.Renderer` to `{0,0}`, silently rewriting any stored selection.

### 1.2 The compute renderer is the porting asset

`ComputeRenderer3D` is the DS software rasterizer translated to GPU compute: CPU builds per-polygon span setups and per-scanline work indices, then 9 compute dispatch stages per frame do span interpolation, coarse+fine tile binning, per-variant rasterization (one indirect dispatch per active variant, up to `MaxVariants`=256, `GPU3D_Compute.h:166`), depth/blend resolve in submission order (with the DS's ±0x200/±0xFF depth-equal tolerances), and a final pass (edge marking, fog, AA) into an `rgba8` image (`GPU3D_Compute.cpp:1059-1216`, `GPU3D_Compute_shaders.h`).

It is nearly Vulkan-shaped already:

- Born on the Switch under **deko3d** (a Vulkan-like API), ported to GL 4.3 (PR #2041, merged 13 May 2024). Dead libnx/deko3d-era Switch code remains commented out at `GPU3D_Compute.cpp:1222-1252` (`armGetSystemTick`, `armTicksToNs`, `EmuQueue.waitIdle`).
- Uses **SSBO atomics plus workgroup shared-memory atomics with `barrier()`** — no image atomics, no subgroup ops (the `gl_SubGroupInvocationARB`/ballot path in BinCombined is `#if 0`), no 64-bit ints (the 64/32 division uses `umulExtended` on 32-bit halves, `:383-388`). The shared-memory atomic is `shared uint mergedMaskShared` (`:925`) with `atomicOr` + `barrier()` at `:955-959` — 4 bytes against a 16 KiB floor, but a *distinct portability class* from SSBO atomics, and it sits under a workgroup size this plan makes a specialization constant.
- Shader variants are generated by prepending `#define`s (33 programs, `GPU3D_Compute.cpp:78`, recompiled on scale change through the incremental `ShaderCompileStep` loop).
- The texture cache is already API-generic: `Texcache<TexLoaderT, TexHandleT>` (`GPU3D_Texcache.h:43`) does CPU decode of all DS formats to RGB6A5 with xxhash-based VRAM-dirty invalidation; the GL-specific part is ~30 lines of loader (`GPU3D_TexcacheOpenGL.cpp`). **Independently corroborated**: the Android fork's `GPU3D_TexcacheVulkan.h` ends with `using TexcacheVulkan = Texcache<TexcacheVulkanLoader, TexcacheVulkanLoader::TextureHandle>;` — exactly this instantiation (§1.3).

Port frictions, now enumerated honestly — the first three are **not** mechanical:

1. **No buffer is per-frame versioned, and nothing fences.** Every buffer is single-instanced and reused every frame; the code relies entirely on GL's implicit in-order guarantee. CPU-written per frame via `glBufferSubData` straight into live buffers: `YSpanSetupMemory`, `YSpanIndicesTextureMemory`, `RenderPolygonMemory` (`GPU3D_Compute.cpp:974-983`), `MetaUniformMemory` (`:1055-1057`). GPU read-modify-written across the 9-stage chain: `TileMemory[3]`, `FinalTileMemory`, `BinResultMemory`, `WorkDescMemory`, `XSpanSetupMemory`. There is no `glFenceSync`, no `glFinish`, no `glClientWaitSync`, no `glMapBufferRange` anywhere in the file, and every buffer is `GL_DYNAMIC_DRAW` with no orphaning. **Vulkan provides no equivalent guarantee.** This is the single most consequential difference and it drives the design in Part 2.
2. **The std140 `MetaUniform` block** (binding 0, `GPU3D_Compute_shaders.h:355-374`, 592 bytes, `GPU3D_Compute.h:190-205`) is prepended to every program and rewritten every frame. Revision 1 never mentioned it — not in the friction list, not in the descriptor design, not in the limits checklist.
3. **`MaxWorkTiles` is an unclamped ceiling.** `GPU3D_Compute.cpp:359` sets `MaxWorkTiles = TilesPerLine*TileLines*16` (16 = assumed max overdraw), and the allocator is an `atomicAdd` with no bound (`GPU3D_Compute_shaders.h:988`), consumed at `:1003` and `:1263`. Under GL this was silently survivable; **in Vulkan it is undefined behaviour unless `robustBufferAccess` is enabled**, and the derived indirect z-count is likewise unclamped (§Phase 1). The index is packed into 21 bits (`:1003`), so the structural ceiling is 2²¹.
4. Mechanical: GL binding indices are reused across pipelines (binding 2 is `YSpanSetupsBuffer` *and* `ColorTileBuffer`, which never co-occur) and need per-pipeline set layouts; `bool` members in std430 blocks become `uint`; the four loose `layout(location=N)` uniforms in Rasterise become push constants (24 bytes); `glMemoryBarrier` calls become explicit `vkCmdPipelineBarrier2` chains. **Descriptor-pool sizing is not the GL binding count**: 8 distinct SSBO bindings over **10** distinct storage-buffer objects once friction 5 converts `SetupIndices`, plus one UBO — and the pool must cover the GPU-internal set once *plus the CPU-written set × N slots* (Part 2), per pass layout, per frame-reset generation.
5. **`uimageBuffer SetupIndices` should not be ported as a texel buffer.** It needs 131,072 elements at ScaleFactor 1 against a spec floor of 65,536 — a floor device fails `vkCreateBufferView` at the scale Phase 2 ships. The data is a plain array of `struct SetupIndices { u16 PolyIdx, SpanIdxL, SpanIdxR, Y; }` (`GPU3D_Compute.h:137-140`) read once per invocation; **as a std430 SSBO of `uvec2` with `bitfieldExtract` it is bit-identical**, adds one SSBO to InterpSpans (3 → 4, still below Rasterise's 7), and removes the limit from the checklist entirely.
6. **The nine wrap-mode samplers live on the renderer, not the texcache.** They are GL sampler objects created in `ComputeRenderer3D::Init` (`GPU3D_Compute.cpp:216-224`), selected host-side per variant at `:789`, bound at `:1163`. Nothing in the texcache owns wrap state. (The per-draw wrap mutation revision 1 cited is in the *classic* GL renderer, `GPU3D_OpenGL.cpp:806-807`, which is out of scope.)

The classic GL renderer, by contrast, leans on GL-isms that translate poorly (stencil bit-plane mid-pass clears, per-batch texture-wrap mutation, `GL_MAX` blend tricks — 49 `glBlend*`/`glStencil*` calls in `GPU3D_OpenGL.cpp`) and its edge-marking/AA is partly non-functional today. It stays as the weak-GPU fallback (an open contributor PR, #2642, proposes lowering it to GL 3.1); porting it buys nothing.

### 1.3 Prior art (melonDS × Vulkan) — corrected

Revision 1's prior-art section contained five factual errors, each of which was load-bearing. The corrected record:

- **Requested since February 2021** (#984, #1060, #2085). **#984** "Vulkan/Metal(MoltenVK) Rendering backend" (Wunkolo, 3 Feb 2021, still open) is the earliest genuine request and also asks to "remove OpenGL-coupling from `core`" — exactly the decoupling this plan schedules. Six days later the same author merged **PR #990** "Allow for a more modular renderer backends" (9 Feb 2021), whose description names Vulkan as a backend the abstraction is meant to admit. That is the `Renderer3D` interface this plan plugs into. (#990 does not formally close #984; treat the link as observed sequence, not stated causation.) **#807 is not a Vulkan request** — it is titled "macOS" and does not mention Vulkan; revision 1 miscited it.
- **PR #2700 is not a feasibility proof.** "Vulkan driver" (PascalPixel) was opened 17 Jul 2026 and **closed 18 Jul 2026 by its own author** — 29 commits, **0 reviews, 0 maintainer comments**. The author self-withdrew after reading an unrelated maintainer comment. **Upstream has never expressed any opinion on this PR or on a Vulkan backend at all.** An unreviewed, unmerged, self-withdrawn branch is evidence that someone wrote Vulkan code; it is not evidence the result was correct. **Do not use it to size any phase.**
- **There is no no-AI-code policy.** `CONTRIBUTING.md` is a style guide; a grep for AI/LLM terms across `CONTRIBUTING.md`, `README.md` and `.github/` returns zero hits, and there is no PR template or policy document. The only data point is one maintainer comment on an unrelated RetroAchievements PR (#2529) objecting to AI-generated code in that PR — a per-PR quality judgement, never applied to graphics work.
- **melonDualDS/WatermelonDS ships a Vulkan `Renderer3D`, but it is not a port of `ComputeRenderer3D`.** In the core fork (`SapphireRhodonite/melonDS-android-lib` @ `GBARumble_PR`), the Vulkan sources are compiled **unconditionally** while `GPU3D_Compute.cpp` appears **only** inside `if (ENABLE_OGLRENDERER)`. `GPU3D_Vulkan.h` declares a graphics-pipeline renderer (`BackendMode::GraphicsHardware`, `CompatibilityGraphicsBackend`/`FastPathGraphicsBackend`, ~30 `GraphicsOpaquePipelineCount` arrays, a `GPU3D_AcceleratedFrontend.h` that does not exist upstream) on a different variant scheme from upstream's flat 256. Its README lists Vulkan *and* compute as separate renderers. **What it does prove, and this is worth keeping:** a Vulkan `Renderer3D` can be built against melonDS's existing interface and its API-generic texture cache. (Caveat: established from headers and `CMakeLists.txt`; the `.cpp` bodies were not read.)
- **Maintainer effort is visibly going into OpenGL; nothing states a position on Vulkan.** The `blackmagic3` branch (last commit 31 Jan 2026) is the 2D-renderer rework now in-tree as the `GPU_Soft`/`GPU_OpenGL` + `GPU2D_Soft`/`GPU2D_OpenGL` split — real, and load-bearing for Phase 4. PR #2642 is an **open, unmerged contributor PR**, not maintainer direction.
- **paraLLEl-RDP** (`Themaister/parallel-rdp`, MIT) is now the *only* external production Vulkan compute rasterizer this plan can point at — different console, different renderer, written by a graphics specialist. A structural pattern source for timeline-semaphore sync and specialization-constant variants; **not a schedule anchor.**

### 1.4 Lessons from other emulators

- **DuckStation/PPSSPP/Dolphin** all abstract over graphics APIs, at the cost of large, long-lived abstraction layers grown over years. That is the argument for this plan's no-RHI decision and it stands on its own. *(Revision 1's Citra citation is deleted: the repository is gone — `github.com/citra-emu/citra` returns 404, so an implementer cannot check it — and the premise was wrong, since the PICA200's vertex and geometry stages are programmable microcode that Citra decompiled to host shaders. With it goes the "infrastructure dominates" claim that was revision 1's stated basis for its phase shape — and which contradicted its own XL-on-rasterizer/M-on-infrastructure estimates.)*
- **melonDS does not have the shader-explosion problem** that forced Dolphin's ubershaders and async-pipeline machinery. The shader set is closed: 33 compute programs plus, for Phase 4, **9 graphics pipelines built from 7 graphics programs** (§Phase 4). Everything can be built at init. Do not build async shader infrastructure.
- **Qt + Vulkan**: `QVulkanWindow` is the wrong shape (owns device/swapchain, drives rendering from Qt's event loop — incompatible with an emu-thread renderer). Dolphin/DuckStation pattern: backend creates `VkSurfaceKHR` from native window handles; **Wayland is the known trap** (Qt owns the `wl_surface`).
- **Runtime SPIR-V emission is overkill** for a static shader set; build-time compilation removes the runtime dependency entirely. (It does **not** remove runtime *pipeline* compilation — see Part 2.)

## Part 2 — Headline decisions

| Decision | Choice | Rationale |
|---|---|---|
| **Vulkan baseline** | **Vulkan 1.3**, no pre-1.3 fallback; software/GL remain the fallback renderers. **Name which limit binds, because they differ** (§2.1): a device at *every* 1.3 floor reports `maxPerStageDescriptorStorageBuffers` = 4 and is **rejected outright** by the acceptance gate; among devices that pass the gate, `maxComputeWorkGroupInvocations` = 128 caps ScaleFactor at **4** (TileSize² is 256 from 5× and 1024 from 9×) and `maxStorageBufferRange` = 128 MiB caps it at **6**. The advertised 1–16× range assumes a device well above the floors. Enable `VK_KHR_portability_subset` when present; **do not request `VK_KHR_portability_enumeration` unless a real loader is present** (§Phase 1). | 1.3 covers the target hardware and avoids an extension-permutation matrix. The legacy class (NVIDIA Fermi/Kepler, Windows Haswell/Broadwell, Windows GCN 1/2) stays on the GL renderers; the selection UI must say so, which requires the reporting path Phase 2 now adds. The prize is macOS via MoltenVK, where GL caps at 4.1 and the compute renderer is currently impossible. Android is out of scope; the design (no subgroups, no image atomics, no 64-bit) keeps a later 1.1+extensions backend feasible. |
| **First (and only) 3D port target** | **`ComputeRenderer3D`**, not the classic GL renderer. | Software-rasterizer accuracy; already survived deko3d→GL; its feature set maps cleaner to Vulkan; unlocks macOS. Unchanged by the review — the strongest decision in the plan. |
| **Frames in flight / buffer versioning** *(new row — the gap that broke revision 1)* | **One 3D chain in flight on the GPU; N=2 slots for CPU-written data.** Version the CPU-written set (`YSpanSetup`, `YSpanIndices`, `RenderPolygon`, `MetaUniform`) as per-frame suballocations from the staging ring; keep **one** copy of the GPU-internal set (`TileMemory[3]`, `FinalTileMemory`, `BinResultMemory`, `WorkDescMemory`, `XSpanSetupMemory`, framebuffer). **One submission per 3D frame**, and frame N+1's submission waits the timeline value frame N signalled — a semaphore signal is a submission-granularity operation, so "frame N complete" is the only value the design expresses; do not write a rule about DepthBlend-vs-ClearCoarseBinMask that a single submission cannot deliver. **The host side is a separate rule and must be stated, because a GPU-side wait does not throttle the CPU:** before writing slot *i*, the emu thread `vkWaitSemaphores` on the value that retired the frame which last used slot *i*. In Phase 2 the `GetLine` readback already provides that wait; **Phase 4 drops the readback and must add the explicit host wait**, or N=2 becomes unbounded CPU run-ahead. | The asymmetry decides it at high scale: the CPU-written set is **18 MiB at 16×**, the GPU-internal set is **2841 MiB**, so duplicating the expensive half costs 2.8 GiB to overlap two 3D chains that will not usefully overlap there anyway. Note the asymmetry inverts at low scale — the GPU-internal set is 22.9 MiB at 1× — so if measurement shows the serialisation costs real frame time at the scales people use, duplicating it below some ScaleFactor is a cheap, later, purely additive change. What N=2 buys as specified is **CPU-setup/GPU-execution overlap only**. Revision 1's "two frames in flight" plus "CPU setup copied near-verbatim" was a straight write-after-read race (§1.2 friction 1). |
| **Shader toolchain** | **Build-time GLSL→SPIR-V with `glslangValidator`** (`--target-env vulkan1.3`), using **glslangValidator's own `uint32_t` C-header output** — no custom CMake binary-embed step. **Specialization constants** for config-derived values (screen dims, TileSize, MaxWorkTiles; workgroup sizes via `local_size_x_id`); the rasterizer-variant matrix as build-time permutations. **No runtime *GLSL* compilation. Pipeline creation remains a real init and scale-change cost** — `vkCreateComputePipelines` compiles on every driver, and on MoltenVK also converts SPIR-V→MSL. **Therefore: keep the `NeedsShaderCompile`/`ShaderCompileStep` time-slicing and OSD machinery, retargeted at pipeline creation.** | The variant space is closed, so build-time GLSL removes MBs of runtime dependency (matters for `BUILD_STATIC` MinGW/BSD) and keeps glslang's multi-licence tangle out of the shipped binary entirely. But revision 1's "eliminating runtime compilation entirely" was false, and it deleted the one piece of machinery that keeps a 33-pipeline rebuild from freezing the UI on every hi-res slider drag — worst on MoltenVK, the platform this plan is for. |
| **Loader / bootstrap / memory** | Vendored **volk** (dlopen), **vk-bootstrap**, **VMA**, under `src/vulkan/`. **One loader story: volk dlopen, and no `vulkan-loader` package on any build path** — but `vulkan-headers` on *every* path, including BSD, and one VMA source, not two. **On macOS a real Vulkan loader ships alongside MoltenVK** (§Phase 1). | Sensible and consistent with existing vendoring precedent. Revision 1 was incoherent here: it argued dlopen-no-link-dep while adding loader packages to four package lists, and specified both a vendored VMA and a vcpkg VMA. |
| **Memory budget** *(new row)* | **A table, not a parenthetical — see §2.1.** **2.81 GiB** of device-local memory for the 3D renderer at 16× with N=2 slots, rising to **~4.0 GiB** once Phase 4's `GPU_Vulkan` and two `GPU2D_Vulkan` units are added. Separately, `maxStorageBufferRange` caps ScaleFactor at **6** on a device reporting the 128 MiB floor — a *descriptor-range* limit, not a memory limit, and one that buffer splitting can lift. | Revision 1's "allocation profile is tiny and static … ~800 MB at 16×" was one tile layer of three. This is the dominant engineering constraint on the advertised 1–16× sweep, not a footnote. |
| **WSI / Qt integration** | **No `QVulkanWindow`, no QRhi.** A `ScreenPanelVK` sibling of `ScreenPanelGL`, plus a presenter shaped like `GL::Context`, creating `VkSurfaceKHR` from `WindowInfo` native handles. Rendering and presentation stay on the **emu thread** — but **the borrow/park protocol is kept and generalized, not deleted**, extended to cover the panel delete, with the lost-wakeup race fixed and a **bounded acquire** so a blocked present can never starve `handleMessages`. **Hoist only `getWindowInfo()` into `ScreenPanel`**; the `WA_PaintOnScreen`/null-`paintEngine` setup moves to a new intermediate class shared by `ScreenPanelGL` and `ScreenPanelVK`. | Minimum-diff, Dolphin/DuckStation-proven, and `WindowInfo` already carries the handles. Revision 1's "borrow hooks become no-ops" was the one decision the review called an application-level hang rather than a bug: a blocked emu thread never reaches `handleMessages` (`EmuThread.cpp:445`), so every UI `waitMessage()` blocks forever. Hoisting the paint setup would separately have broken `ScreenPanelNative` — the very fallback Phase 2 depends on. |
| **Descriptors** | One descriptor-set *layout* per pass — but several *sets* per layout, which is where the per-frame and per-variant variation lives: N sets for the CPU-written slots, 9 for the wrap modes, and one per active texture. **Push constants** (24 bytes) for per-dispatch scalars; a per-frame slot or dynamic UBO for `MetaUniform`. For the 256-dispatch rasterization loop: split the combined sampler into separate image + sampler bindings, and **pre-bake nine descriptor sets differing only in which wrap-mode sampler sits at the sampler binding** — bind the right one per variant. Per-variant texture sets from a per-frame-reset pool; deferred destruction of evicted texcache images keyed by timeline value. No descriptor indexing, no bindless. | The wrap mode is **already a host-side decision** (`GPU3D_Compute.cpp:1160-1164` picks `variants[i].Sampler` before the dispatch), so revision 1's push-constant-indexed sampler array bought nothing while introducing a hard dependency on `shaderSampledImageArrayDynamicIndexing` — which core Vulkan 1.3 does **not** guarantee (required only from 1.4, or with `descriptorIndexing`), and whose silent-failure mode is every polygon sampling with CLAMP wrap. Pre-baking removes the dependency instead of gating on it. |
| **Sync** | One **timeline semaphore** as the frame-progress clock, signalled once per submission, plus **binary semaphores for swapchain acquire/present** (timeline semaphores cannot be used there). ### 2.1 Memory model and device requirements

**Per-scale geometry** (derived from `GPU3D_Compute.cpp:337-359` + `Utils.h:42-53`): TileSize is 8 for S=1–4, 16 for S=5–8, 32 for S≥9. `TilesPerLine*TileLines*TileSize²` is identically `ScreenWidth*ScreenHeight`, so **`TileMemory` is TileSize-independent**: `64 × 256 × 192 × S²` = 3 MiB × S² per layer, three layers.

| S | GPU-side (1 copy) | CPU-written (per slot) | **3D total, N=2** | + Phase-4 2D | **Full compositor** |
|---|---|---|---|---|---|
| 1 | 22.9 MiB | 3.0 MiB | **28.9 MiB** | 4.3 + 46 | ~79 MiB |
| 4 | 222.1 | 6.0 | **234.1** | 69 + 46 | ~349 |
| 8 | 765.1 | 10.0 | **785.1** | 276 + 46 | ~1107 |
| 12 | 1634.1 | 14.0 | **1662.1** | 621 + 46 | ~2329 |
| 16 | 2841.1 | 18.0 | **2877.1 MiB = 2.81 GiB** | 1104 + 46 | **~4.0 GiB** |

At 16×, 3D: `TileMemory[i]` = 768 MiB × 3 = 2.25 GiB; `FinalTileMemory` 288 MiB; `XSpanSetupMemory` 192 MiB; framebuffer 48 MiB; index buffer 16 MiB; `BinResult` 6.1 MiB; `WorkDesc` 3 MiB; the rest ~2 MiB; plus a second CPU slot at 18 MiB. Phase 4 adds 3 MiB × S² for `GPU_Vulkan` **plus 1.3125 MiB × S² for the two `GPU2D_Vulkan` units** (`OBJLayerTex`, `OBJDepthTex`, `OutputTex` per unit) plus ~46 MiB of scale-independent BG-layer and sprite textures. **Texcache footprint is unbounded in the code and must be instrumented, not estimated.**

**`maxStorageBufferRange` is a descriptor-range limit, not a buffer-size limit** (`VUID-VkWriteDescriptorSet-descriptorType-00333`); `VkBuffer` size is bounded by `maxBufferSize`/`maxMemoryAllocationSize`, whose floors are 1 GiB. On a device reporting the 128 MiB range floor the binding search gives **S ≤ 6** (TileMemory), S ≤ 10 (XSpanSetup, FinalTile).

**Splitting lifts the storage-range clamp from 6 to 16. It does not lift a floor device's real ceiling, which is 4** — `maxComputeWorkGroupInvocations` = 128 against TileSize² (256 from 5×, 1024 from 9×), and no amount of buffer splitting changes a workgroup size. Splitting is therefore work for devices with **≥1024 invocations but a small `maxStorageBufferRange`**, not for a device at every floor. Decide from measured driver data whether that population is worth the code before building it.

The scheme, if built: **split each tile layer into K chunks at whole-work-tile granularity** — bind the chunks to **K distinct bindings selected by an unrolled `switch` on a specialization constant**, not as a descriptor array. Both chunk indices are workgroup-uniform (Rasterise's `workDesc` is loaded once per workgroup at `GPU3D_Compute_shaders.h:1076`, DepthBlend's `workIdx` derives from `linearTile` at `:1326`), so an array *would* be legal — but indexing an array of storage-buffer descriptors at all requires `shaderStorageBufferArrayDynamicIndexing`, which is **optional in Vulkan 1.3** and required only from 1.4. The unrolled form needs no feature. **Split mode also changes the descriptor budget**, which the acceptance gate below does not otherwise cover: Rasterise goes from 7 storage buffers to 4 + 3K (**22 at the K = 6 needed for 16×**), DepthBlend to 2 + 3K + 3, so in split mode the gate becomes `maxPerStageDescriptorStorageBuffers ≥ 4 + 3·ceil(3 MiB·S² / maxStorageBufferRange)` and the set layouts and pool sizes are K-parameterized. Also **split `FinalTileMemory` on its existing Color/Depth/Attr boundaries** (`:335-337`, zero index arithmetic change) and **resize `XSpanSetupMemory`'s `64*2048*S` guess** (the code comment at `:388-389` already calls it "pretty bad guesses"). Region-splitting does *not* work for `TileMemory`: the work-tile index is a global compaction counter (`:988`), not a screen-space offset.

**Device acceptance — replaces revision 1's checklist, which was wrong in five ways.**

*Hard gate (reject the device, fall back to software/GL):* `apiVersion ≥ 1.3`; a compute queue family; **`maxPerStageDescriptorStorageBuffers ≥ 7`** (Rasterise's real count; the spec floor is 4, so a gate is warranted — but revision 1's `≥ 10` rejected conformant devices for nothing). **Note what this implies: a device at *every* 1.3 limit floor reports 4 here and is rejected outright. The scale analysis above and the clamps below apply only to devices that pass this gate.**

*Clamp inputs for the offered ScaleFactor (take the minimum):* `floor(sqrt(maxStorageBufferRange / 3145728))`; `floor(maxStorageBufferRange / 12582912)`; `floor(sqrt(maxStorageBufferRange / 1179648))`; `floor(maxImageDimension2D / 256)`; `maxComputeWorkGroupInvocations` (≥64 → S≤4, ≥256 → S≤8, ≥1024 → S≤16); **the probed max TileSize from actual `vkCreateComputePipelines` success**; **the probed allocatable working set**.

*Two dispatch dimensions that must be chunked, not clamped.* `maxComputeWorkGroupCount[0]`: InterpSpans dispatches `maxYSpanIndices/32` = 4096·S groups, so the required floor of 65535 gives S ≤ 15 — and essentially every AMD, Intel and Mesa device reports exactly 65535, so a clamp here would cost 16× on most hardware for no reason. **Chunk the dispatch against the queried limit instead.** `maxComputeWorkGroupCount[2]`: the indirect z-count is GPU-written by an unclamped `atomicAdd` (`GPU3D_Compute_shaders.h:1002`) and its ceiling `MaxWorkTiles` exceeds 65535 for S = 3–8 and 10–16. No host query can bound it; revision 1 recorded it "for ScaleFactor clamping", which it cannot serve. **Fix in-shader**: clamp against a specialization constant equal to the queried limit, or restructure to `(ceil(z/N), 1, N)`.

*Device features.* Revision 1 enabled none, which is why the two real dependencies went unnoticed. They fall into two groups, and the distinction matters because requesting an unsupported feature at `vkCreateDevice` fails device creation outright:

- **Unconditionally enabled** (all guaranteed on any 1.3 device): `synchronization2`, `timelineSemaphore`, `maintenance4`, `dynamicRendering` (Phases 3–4), `robustBufferAccess`.
- **Queried, then enabled only if `VK_TRUE`**: **`independentBlend`**, needed by Phase 4's sprite pass and *not* core-guaranteed through 1.3. A device lacking it is still **accepted**; Phase 4's full compositor is disabled and the user gets Phase 2's soft-composited mode.

`shaderSampledImageArrayDynamicIndexing` is **no longer needed** given the pre-baked wrap-mode descriptor sets, and `shaderStorageBufferArrayDynamicIndexing` is not needed given the unrolled-switch form of the splitting scheme. Do not request `fragmentStoresAndAtomics`, `shaderInt64`, or subgroup ballot — nothing uses them.

*On `robustBufferAccess`, one lifetime, not three:* it is **permanently on**, not a bring-up aid. It is the only thing that turns §1.2 friction 3's unbounded `atomicAdd` from undefined behaviour into defined behaviour, and the in-shader clamp is the real fix — but the clamp is Phase-2 work and the feature costs nothing on any device, so keep it enabled in shipping builds too.

*Cannot be queried; must be probed:* the **Metal per-pipeline threadgroup cap** (a device reporting 1024 can still refuse a specific pipeline — probe by creating the Rasterise and DepthBlend pipelines specialized to TileSize 8/16/32 and clamp on success). **This probe needs the real shaders, so it lands in Phase 2, not Phase 1** — Phase 1 records the reported limits and leaves the probe hook; Phase 2 fills it in and re-runs it on every settings change, never lazily when the user drags the slider. Also probe **actual allocatable memory** (heap sizes are not availability — attempt the working set through VMA and treat `VK_ERROR_OUT_OF_DEVICE_MEMORY` as the clamp signal, allocating the largest buffer first so failure is early).

### Phase 1.5 — Validation harness (M–L) — *new; revision 1 priced this at zero*

**Goal:** make Phase 2's correctness argument executable. Deliverables (~2,500–3,500 LOC, almost none of it graphics work):

- **Frame-hash mode** in both renderers, plus the normalizer. **The normalization is exactly UNORM8 quantization of a 6:6:6:5 value**, and it is invertible: forward error is ≤ 0.5·63/255 = 0.1235 < 0.5, and ties never occur (a tie needs 21 | r6, giving r6 ∈ {0,21,42,63} → exact integers), so the mapping is vendor-independent both ways. **Hash in packed space**, converting the GL side down: `r6 = (R8*63 + 127)/255` etc. Four traps revision 1 did not mention: parity is defined only at 1× (no downscale exists); hash the **pre-`RenderXPos`** buffer on both sides; software output is indexed `ColorBuffer[line*258 + 259 + x]`, not a dense 256 stride; and leave the bit-30 block at `GPU3D_Compute_shaders.h:1665-1668` commented out.

Generate `Polygon`/`Vertex` sets covering the closed variant space (5 blend modes × textured/untextured, shadow mask/shadow, W vs Z buffer, the 8 final-pass permutations, toon/highlight, clear-bitmap, fog, edge marking, AA). Better coverage than any game frame and trivially licensable.

- **Add a fallback-reporting path**: a renderer-kind accessor or out-param on `GPU::SetRenderer` so the frontend can learn the fallback fired, un-latch `lastVideoRenderer` (`EmuThread.cpp:878`), surface a message, and show reality in the settings UI. Without it the plan's own requirement — tell excluded-hardware users explicitly rather than fail silently — is unimplementable.
- Modify `EmuInstance.h` (add `renderer3D_Vulkan` with an explicit value), `EmuThread.cpp:858-889` (construction arm), `Config.cpp` (`3D.Vk.*`), `VideoSettingsDialog.cpp` (radio). **Grey out the ScaleFactor control when the Vulkan radio is selected in this phase** — scale is hard-locked to 1× until Phase 4, and shipping a live 1–16× slider that silently does nothing is the same defect Phase 4 has to fix anyway (`setEnabled` precedent at `VideoSettingsDialog.cpp:43-50`).
- **Output contract.** The compute renderer's final pass writes display-normalized `rgba8` (`GPU3D_Compute_shaders.h:1673-1675`), but `GetLine` consumers require the software renderer's packed format: 6-bit R/G/B at bits 0/8/16 and 5-bit alpha at bit 24 (`GPU3D_Soft.cpp:562`; `DrawBG_3D` tests `(c >> 24) == 0`, `GPU2D_Soft.cpp:371-382`; `DoCapture` extracts the same lanes, `GPU_Soft.cpp:310-399`). **The shader already carries that exact packed u32 in `color.x` throughout the final pass** and converts only at the very end (`GPU3D_Compute_shaders.h:1673-1675`) — **so Phase 2's readback variant simply stores `color.x` instead of the `vec4` conversion.** Do not cite the packing assignment at `:1656` as the source: it is inside `#ifdef AntiAliasing` → `if (coverage != 0)` and is one of several writers to `color.x`, not the general form. *(Revision 1 pointed at `:1665-1668`, which is a commented-out alpha test setting bit 30; `GPU3D_Soft.cpp:562` has no bit 30 and `GPU2D_Soft.cpp:380` applies `0x40000000` consumer-side. Leave it commented.)*

  **The readback path, specified:** final pass writes a **device-local** buffer → `vkCmdCopyBuffer` into the host-visible ring → barrier with `dstStageMask` HOST / `dstAccessMask` `HOST_READ` **before** the timeline signal the host waits on. Prefer `HOST_VISIBLE|HOST_CACHED` with explicit invalidate over COHERENT write-combined. **`GetLine` memcpys the line into a cached scratch buffer once** and hands consumers that pointer — reusing the existing `ScrolledLine` shape in `SoftRenderer3D::GetLine` (`GPU3D_Soft.cpp:1806-1850`) — so `DrawBG_3D` (256 scalar reads/line × 192) and `DoCapture` never read device memory scalar-wise.

  **`GetLine` must return a valid 256-u32 pointer in every state, never nullptr.** Give the ring a zero-initialized fallback slot that `Reset()` selects, covering all four no-valid-slot states: first frame after Init/Reset, the frame after a settings-change reallocation, an abort/restart frame, and `RenderFrameIdentical` on frame 0.

  **An identical frame submits nothing** (`GPU3D_Compute.cpp:636-640`), so its timeline value would never signal and any wait on it hangs forever. The renderer must still **advance the frame's timeline value** and keep serving the previous ring slot — mirroring the software renderer, which posts all 192 scanline signals in its `FrameIdentical` branch (`GPU3D_Soft.cpp:1789-1791`) precisely so consumers never block on work that was never issued. State this as an invariant on the clock, not just on the buffer.

  **`RestartFrame` = re-submit from the already-uploaded geometry state, not discard** (§1.1). **`PreSavestate` = drain.** **While `AbortFrame` is set, `GetLine` returns black without waiting and `FinishRendering` skips its wait** — matching `GPU3D_Soft.cpp:1807-1814` and `:1740-1743`. `AbortFrame` is savestated and can be true before the first submission after a state load; make it a test case.

  **Timing honesty.** First `GetLine` arrives ~48 scanlines after submission — **~3 ms at 100% speed, ~0.5 ms at 600%, effectively zero under fast-forward** (§1.1). The risk is *fast hosts and fast-forward*, not slow GPUs, and IMMEDIATE/MAILBOX does nothing about it because the stall is a readback host-wait, not a present. **Chunked line-range readback signalled at increasing timeline values is a Phase-2 requirement, not a prepared mitigation** — or state explicitly that fast-forward is degraded on the Vulkan path and by how much. Scale locked to 1× this phase.
- **macOS**: reachable only because Phase 1 now ships the loader and MoltenVK. **MoltenVK serializes the dispatch loop** — `MTLDispatchTypeSerial` for all non-occlusion uses — so ~256 back-to-back indirect dispatches become ~256 strictly serialized ones, many covering only a handful of work tiles where launch latency dominates. Measure on real Metal hardware **early in this phase**, not in Phase 5. If it is too slow, the options to consider are merging low-occupancy variants or a single dispatch with a variant index read from the work descriptor.
- **Validation:** (a) sync-validation + GPU-AV clean over a stress matrix (Zelda PH/ST, translucency, SM64DS); (b) the Phase-1.5 oracle — hashes in packed space, or the software-diff baseline if the GL twin is cut; (c) corpus replay on lavapipe in CI; (d) savestate loops, VCOUNT-write titles, boot-to-first-frame, mid-game settings change, hot-swap soak; (e) measured first-`GetLine` wait **and time spent inside `DrawBG_3D`/`DoCapture`** on lavapipe and MoltenVK; (f) **cold- and warm-`VkPipelineCache` build time for the full pipeline set** on a desktop driver and on MoltenVK — the number that says whether the time-slicing above is sufficient.
- **Risks:** barrier bugs (sync validation from day one — **and note macOS cannot validate them**); the fast-forward deadline; descriptor/texture lifetime across texcache eviction (deferred destruction keyed by timeline value).

### Phase 3 — Vulkan presentation path (L)

**Goal:** swapchain-backed display, initially presenting software-composited RAM frames, so it is testable with any renderer.

- New `VulkanPresenter.{h,cpp}` implementing a `GL::Context`-shaped interface: `Create(WindowInfo)`→surface+swapchain (FIFO default), `SwapBuffers`→acquire/draw/present with `OUT_OF_DATE`/`SUBOPTIMAL` handled on **both** acquire and present, `SetSwapInterval`→present-mode change, `CreateSharedContext`→same `VkDevice`, per-window swapchain. **Binary semaphores for acquire/present** (timeline semaphores cannot be used there). **Bounded acquire with a skip-present-on-timeout policy** — non-negotiable, because `handleMessages` is only reached once per emu-loop iteration (`EmuThread.cpp:445`).
- New `ScreenPanelVK`: sibling of `ScreenPanelGL`, deriving from a **new intermediate native-surface class** alongside it, leaving `ScreenPanelNative` on the plain `QPainter` path. RAM frames→staging ring→sampled image; screen quads via `screenMatrix[]`; OSD via staging. Teardown on `QPlatformSurfaceEvent::SurfaceAboutToBeDestroyed`; resize signalled UI-side, executed render-side; multiply by `devicePixelRatio`.
- **Generalize the borrow/park protocol** (`borrowPresenter`/`returnPresenter`): the emu-side handler waits the presenter's timeline value and marks presenters unusable instead of `DoneCurrent`; **extend the bracket to cover the panel delete at `Window.cpp:813-815`** and drop the `windowID != 0` condition; **fix the lost-wakeup** with a `borrowRequested` flag under the mutex and a `while` loop; fan out over all windows. **Presentation must take `renderLock`** — `ScreenPanelGL::drawScreen` does not today.
- **Frontend CMake work, never previously mentioned:** per-platform surface sources in the existing platform arms (`VK_KHR_win32_surface`; `VK_EXT_metal_surface` via an ObjC++ shim that attaches a `CAMetalLayer` to the `NSView` from `WindowInfo`; xlib/xcb and — inside the existing `ENABLE_WAYLAND` block — wayland). **`find_library(QUARTZCORE_LIB QuartzCore)` and `COCOA_LIB` must be linked whenever the shim compiles, independent of `USE_QT6`** — today `COCOA_LIB` sits inside a `NOT USE_QT6` guard and `USE_QT6` defaults ON, so it is never linked in any shipping macOS build, and QuartzCore is linked nowhere in the tree.
- **Wayland gated off at first ship**; two prepared fallbacks. Design now for both inversions: Wayland surfaces generally never report `OUT_OF_DATE` (`currentExtent` is `0xFFFFFFFF`, so resize must work from the Qt-side signal alone), and Mesa's Wayland WSI blocks acquire/present for occluded windows in FIFO — with up to 4 windows presented sequentially, one hidden window must not stall the rest, so **skip-present on occlusion, and use MAILBOX or `VK_EXT_swapchain_maintenance1` where available**.
- **Validation:** resize/rotate/fullscreen/DPI stress; vsync + fast-forward toggles; 2–4 windows; multi-instance; **software renderer with `Screen.UseGL=false` still displays**; panel swap across every presenter-kind transition; validation clean; X11/Windows/macOS.

### Phase 4 — Full Vulkan compositor: 2D, capture, hi-res, zero readback (XL)

**Goal:** `VkRenderer : Renderer` parent, eliminating the CPU round-trip; hi-res scaling; GPU display capture.

**State the audience plainly**, which revision 1 did not: hi-res requires this compositor → requires an active Vulkan *display* → requires `ScreenPanelVK` → **gated off on Wayland at first ship**. So every Wayland user, every user who keeps the GL display, and every `ScreenPanelNative` user gets **1× only** with a per-frame CPU readback, while the settings dialog offers 1–16×. **Clamp or grey out the ScaleFactor control when the active mode cannot honour it**, and surface the active mode somewhere user-visible so a bug report can say which one. Consider whether promoting Wayland enablement is worth more than this compositor.

- New `src/GPU_Vulkan.{h,cpp}`: port of `GPU_OpenGL.cpp` — batched scanline-range compositing, final pass, `DoCapture`/`DownscaleCapture`, `SyncVRAMCapture` via download buffer + fence, reusing the exact `SyncAllVRAMCaptures`-before-swap ordering.
- New `src/GPU2D_Vulkan.{h,cpp}`: port of the blackmagic3 `GPU2D_OpenGL` compositor — **the largest untranslated surface in the plan, and not pass-for-pass.** The count is bounded and now known: **9 graphics pipelines from 7 graphics programs**, and only one program multiplies. `DoRenderSprites` mutates per-attachment write masks *between draws inside one pass* (`GPU2D_OpenGL.cpp:1663/1669/1675/1682/1683`), with attachment 0 and 1 differing in all three states — att0 `0x0`/att1 `0xA`, att0 `0x0`/att1 `0x4`, att0 `0xF`/att1 `0xB`. In Vulkan `colorWriteMask` is pipeline-baked and per-attachment divergence needs `independentBlend`; `vkCmdSetColorWriteMaskEXT` exists only under `VK_EXT_extended_dynamic_state3` (in no core version) and **MoltenVK hard-disables it**. So SpriteShader becomes 3 pipelines. Everything else mutated between draws — depth test/write/compare, viewport, scissor — is core-1.3 dynamic (topology never varies: every draw in both files is `GL_TRIANGLES`); wrap modes become two immutable samplers (`VK_BORDER_COLOR_FLOAT_TRANSPARENT_BLACK`, since `GL_TEXTURE_BORDER_COLOR` is never set in the tree, and getting this wrong produces black seams); and there are **zero** `glBlend*`/`glStencil*` calls in the 2D path, so the classic renderer's stencil/blend problems do not transfer.

  **The real Phase-4 risk is render-pass instance count, not pipeline count.** `GPU.cpp:1156-1157` drives `DrawScanline` once per visible line; worst case is ~3072 `vkCmdBeginRendering` pairs per frame where GL has the same number of near-free FBO binds. Real games are dirty-driven and far below this. **Unknown — must be measured.**

  Two hidden ordering contracts to make explicit: `DoCapture`/`DownscaleCapture` set no depth/stencil/blend/mask state and rely on `RenderScreen` having run first; and `GPU_OpenGL.cpp:771-772` permanently rewrites the wrap mode of shared texture objects, so the final pass samples with `CLAMP_TO_BORDER` after the first capture. Vulkan's image/sampler split removes that aliasing — a real divergence to check when diffing against GL, and exactly the class of difference that gets misattributed to a barrier bug.
- **Mode selection** stays one `renderer3D_Vulkan` value: the full compositor when a Vulkan display is active, otherwise Phase 2's soft-composited mode. **This needs a real degrade hook** — `GPU::SetRenderer`'s fallback hardcodes full `SoftRenderer` (`GPU.cpp:334-338`), so a failing `VkRenderer` would lose the Vulkan 3D renderer entirely. Add a fallback-factory parameter or two-stage construction in `updateRenderer`.
- Modify `GPU.h` + `Screen.cpp:1150`: replace the `*(GLuint*)` convention with a tagged output handle; `ScreenPanelVK` gains the zero-copy path.
- Modify `GPU3D_Vulkan.cpp`: **drop readback when parented by `GPU_Vulkan` — and add the explicit host-side `vkWaitSemaphores` before reusing a CPU-written slot, because the readback wait being removed *was* the host throttle** (Part 2). Enable the ScaleFactor/TileSize matrix with the clamp recomputed from §2.1. If the buffer-splitting scheme is built, it lifts the storage-range clamp from 6 to 16 **on devices that have the workgroup invocations for it**; a device at the `maxComputeWorkGroupInvocations` floor caps at 4 regardless, so splitting is not what stands between a floor device and 16×.
- **Validation:** scale sweep incl. TileSize transitions and clamp behaviour **on real Metal hardware** (a synthetic minimal-limits device cannot catch the per-pipeline threadgroup cap); capture torture with VRAM-content diff; oracle parity at multiple scales; multi-window; hot-swap soak.

### Phase 5 — Hardening & release (M)

*(Loses MoltenVK packaging and pipeline-cache persistence to Phase 1; gains a device-loss policy.)*

- **Wayland enablement** after dedicated testing on GNOME/KDE/wlroots — either the existing native-`wl_surface` path or the child-`QWindow` fallback.
- **Device-loss policy and diagnostics** — absent from revision 1 entirely. Detect `VK_ERROR_DEVICE_LOST` on submit/present, tear down, fall back to software, notify. This needs a runtime error path on the `Renderer` interface, which does not exist today. Without it, a silent fallback plus no mode indicator makes every bug report unactionable.
- Pipeline-cache corruption fuzzing.
- Perf pass: overlap 3D compute with 2D composite on the timeline; evaluate an async-compute queue. **"Expect parity or better" is not an assumption to ship with** — it is contradicted by MoltenVK's serialized dispatch on a 256-dispatch loop, and by the unmeasured render-pass instance count. Measure both.
- Docs (BUILD.md, maintainer notes on barrier structure and binding maps); CI with `ENABLE_VKRENDERER=ON` where the toolchain permits; driver-quirk switches only as encountered.

| Risk | Mitigation |
|---|---|
| **Upstream acceptance is entirely unmeasured** — not hostile, not favourable, unknown. No maintainer has stated a position on a Vulkan backend; the only Vulkan PR was self-closed in ~24h with 0 reviews, producing no signal. There is no codified AI-contribution policy. Maintainer effort is visibly going into OpenGL, which says where attention is, not that Vulkan is vetoed. | **Convert the unknown into an answer before Phase 2.** Open a design issue upstream describing the scope and ask for an explicit yes/no/conditions. | **2D compositor churn** (blackmagic3 is fresh). | Phase 4 pinned to a tag; Phases 1–3 ship value regardless. |
| **Enum/config compatibility** across build-flag combinations. | Explicit enum values in Phase 1 (not Phase 2 — the hazard is already live with `ENABLE_OGLRENDERER=OFF`); clamp unknown values to software. |
